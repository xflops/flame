# Flame 0.7.0-rc3 Release Notes

Status: prepared, not published. No tag, crate, wheel or image for `v0.7.0-rc3` exists yet.

Release branch: `release-0.7`. `v0.7.0-rc3` is a tag on this branch; the source commit is recorded when the tag is created.
Previous release candidate: `v0.7.0-rc2`, a tag on `177541c2`. The changes below are the commits of `release-0.7` since that tag.

## Why rc3

`v0.7.0-rc2` was tagged, its GitHub pre-release was created and its container images were published (`xflops/flame-session-manager`, `flame-executor-manager` and `flame-console` have a `v0.7.0-rc2` tag), but two jobs of its publish run failed, so **the `flamepy` wheel and the Rust crates were not published**: there is no `0.7.0rc2` on PyPI, and no `stdng`, `flame-rs-macros` or `flame-rs` `0.7.0-rc2` on crates.io.

- **`Publish flamepy`.** `hack/release.sh build-python` built and checked the wheel, installed it into a virtual environment, and then failed its last check, `PYTHONPATH="${root}" python3 -c 'import flamepy.app'`, with `No module named 'flamepy'`. The check is given the virtual environment's root, but the package is under `lib/python3.12/site-packages` inside it, so it can never import. The check had not run before: the rc1 publish stopped earlier, in `Release Metadata`.
- **`Publish Rust crates`.** crates.io answered `403 Forbidden: authentication failed` when publishing `stdng v0.1.9`. That is a credentials problem and not a source problem; the token used for publishing (`CARGO_REGISTRY_TOKEN`) has to be checked for publish permission on `stdng`, `flame-rs-macros` and `flame-rs`.

The first is fixed on this branch by #649 (see below). The second is not a code change and is not fixed here (see "Before tagging"). rc3 also carries three more changes made after rc2.

## Changes since rc2

Backported from `main` to `release-0.7`, one pull request each:

- **The release check imports `flamepy` from the directory that holds it (#648, backport #649).** `hack/release.sh build-python` put the root of its virtual environment on `PYTHONPATH`, where `flamepy` is not importable, so `Publish flamepy` failed for rc2. The check now uses the directory that contains the package.
- **Serving sessions accept task options (#641, backport #645).** `flamepy.serving.Session.run(req, option=None)` and `submit(req, option=None)` take `TaskOptions`, for example `TaskOptions(affinity={key})`, so a serving client can use data-aware scheduling. A serving worker already published the keys it holds with `Instance.publish` and `retract`; the client side was missing. The argument is optional, so existing callers are unchanged. The SDK documentation has a new section on data-aware scheduling with the serving helper.
- **Data-aware scheduling breaks equal scores by attribute count, then idle time, then executor ID (#642, backport #646).** Before, the `das` plugin broke equal scores, including every score of 0 when no executor holds the requested key, by the smaller executor ID, so work without a match always went to the same executor. For equal scores it now prefers the executor that publishes fewer attributes (the emptier cache, so work lands where it evicts the least), then the one that has been Idle the longest, then the smaller ID. A better match still wins; only ties change.
- **`agent.open_session` opens or creates a session with a caller-chosen id (#650, #651, backport #652).** `flamepy.agent.open_session(ssn_id=...)` used to reopen an existing session only and failed with `NOT_FOUND` for a missing id. It now creates the session with the given `image`, `min_instances`, `max_instances` and `resreq` when it does not exist; an existing session keeps its own options. Calls without `ssn_id` are unchanged.

## Upgrade Notes

- **Placement of sessions without affinity changes.** The tie-break applies to every session that goes through the `das` plugin, including sessions that carry no affinity. They used to go to the smallest executor ID, which also kept a stateful service on the same executor; they now rotate across executors with equal attribute counts. A service that retains state in executors without publishing attributes, and relies on getting the same executor back, should publish a key for that state.
- Everything in the rc1 and rc2 notes still applies.
